# Приложение Б

## Описание локального кэша SQLite

Локальный файл кэша (типичный путь `data/cache/prognoz.db`) не является промышленной СУБД. Это встраиваемое хранилище ответов API с метками времени и политикой TTL [15].

### Б.1 Назначение таблиц

Таблица Б.1 – Основные таблицы кэша

| Таблица | Назначение |
| --- | --- |
| meta | Ключ кэша, время получения, необязательный ETag |
| competitions | Код и название соревнования, эмблема, время получения |
| matches | Матчи лиги: дата, статус, команды, счёт, гербы, площадка |
| standings | Строки турнирной таблицы |
| team_rosters | Заявка клуба (тренер и состав в JSON), площадка, страна |
| match_lineups | Составы конкретной встречи при наличии в API |

### Б.2 Политика времени жизни

Таблица Б.2 – TTL по типам данных

| Тип данных | TTL |
| --- | --- |
| Расписание / ещё не сыгранные матчи | 6 ч |
| Завершённые матчи | 24 ч |
| Турнирные таблицы | 24 ч |
| Деталь матча (заявка/lineup) | 6 ч |

Повторный запрос к сети выполняется только при отсутствии записи или при истечении TTL, с соблюдением лимита 10 запросов в минуту [7].

### Б.3 Логическая схема (текстом)

– `meta(cache_key PK, fetched_at, etag)`;
– `competitions(code PK, id, name, emblem, fetched_at)`;
– `matches(id PK, competition_code, utc_date, status, matchday, home_id, home_name, away_id, away_name, home_goals, away_goals, winner, home_crest, away_crest, venue, fetched_at)`;
– индекс `idx_matches_comp_date(competition_code, utc_date)`;
– `standings(competition_code, team_id, …, PRIMARY KEY(competition_code, team_id))`;
– `team_rosters(team_id PK, …)`;
– `match_lineups(match_id PK, …)`.

Рисунок логической схемы кэша в основном тексте согласован с файлом `figures/drawio/sqlite-cache.png` (рисунок: таблицы кэша SQLite).

### Б.4 Ограничения

Кэш не моделирует пользователей, платежи и журнал ставок. Резервное копирование корпоративного уровня не требуется: при повреждении файл удаляют и наполняют заново из API.
