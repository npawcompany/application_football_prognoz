# 2 Проектирование

## 2.1 Технологии и архитектура

Выбор технологий подчинён цели: настольное окно, локальный расчёт, умеренный объём зависимостей и воспроизводимость на учебной машине. Язык Python 3.11 и выше даёт удобную работу с HTTP, таблицами и числовыми расчётами, а также зрелую экосистему тестирования [13]. Графический интерфейс строится на Flet: приложение оформляется как нативное окно на Windows и macOS, без обязательного развёртывания отдельного веб-сервера для пользователя [6]. Сетевые запросы выполняются библиотекой httpx [10]. Для разбора CSV истории применяется pandas [12]. Локальный кэш ответов API размещается в файле SQLite [15]. Библиотека scikit-learn входит в стек проекта как инфраструктура обучения и экспериментов на исторических CSV; оперативный контур экрана прогноза в первой версии опирается на явные формулы Эло и Пуассона, а не на непрозрачный классификатор «из коробки» [14].

Архитектура пакета слоистая. Слой экранов обращается только к службам и к предметным типам. Слой служб организует загрузку данных, сбор признаков, вызов модели, таблицу рынков и при необходимости пояснение языковой моделью. Слой данных выполняет HTTP, разбор CSV и запись SQLite и не содержит виджетов. Слой расчёта получает вероятности и предварительный счёт и не выполняет сетевых запросов. Слой пояснения получает уже готовые факты и вероятности и не выбирает исход. Предметные типы не содержат ввода-вывода.

Поток зависимостей показан на рисунке слоёв (рисунок: слои приложения). Контекст системы – пользователь, настольное приложение, источник football-data.org, локальный кэш, дополнительный источник статистики, лента новостей и текстовое пояснение – показан на рисунке контекста (рисунок: контекст системы).

Последовательность расчёта прогноза:

1. Служба матчей читает кэш SQLite; при промахе времени жизни записи обращается к football-data.org.
2. Служба признаков собирает форму, очные встречи, рейтинги Эло, средние голы за пять матчей и места в таблице только из кэша, обрезая историю датой матча.
3. Модуль прогноза возвращает вероятности дома / ничья / гости (сумма равна 1): при малой выборке только рейтинг Эло, иначе смесь Пуассона с весом 0,65 и рейтинга Эло с весом 0,35. Предварительный счёт – мода сетки по средним голам за пять матчей без рейтинга Эло.
4. Таблица рынков строится по той же сетке голов и согласуется с итоговыми вероятностями 1 / X / 2. Угловые, карточки, фолы и пенальти допускаются только при наличии статистики дополнительного источника и в расчёт исхода не входят.
5. Модуль пояснения получает факты, вероятности и таблицу рынков и при необходимости формирует короткий текст. Числа на экране от пояснения не зависят.
6. Интерфейс показывает числа всегда; блок пояснения – только при наличии текста. Итог по новостям строится только по полученным заголовкам.

Диаграмма последовательности для этого сценария вынесена на отдельный рисунок (рисунок: последовательность прогноза).

Сетевой доступ к football-data.org ограничен тарифом поставщика; ответы кэшируются локально, а в журналы приложения не попадают служебные реквизиты доступа к внешним сервисам [7].

Программное обеспечение поставляется как настольное окно. Обязательный браузерный клиент не требуется. Flet может использовать веб-технологии внутри окна, сценарий запуска остаётся настольным.

Разделение ответственности между слоями дополнительно защищает от типичных ошибок первой версии. Если бы представление само ходило в HTTP, тесты интерфейса зависели бы от сети. Если бы модель читала SQLite, математический модуль нельзя было бы прогнать на синтетических признаках. Если бы слой AI считал вероятности, исчезла бы граница между объяснением и классификацией. Принятая схема делает каждую из этих ошибок структурно менее вероятной.

С точки зрения развёртывания первая версия ориентирована на поставку собранного настольного приложения: на Windows – исполняемый файл `.exe`, на macOS – пакет `.app`. Пользователь запускает готовое окно без установки интерпретатора Python и без команд в терминале. Отдельный сервер баз данных не требуется: файл кэша создаётся локально при первом обращении.

При недоступности источника программное обеспечение должно показывать данные из ещё действующего кэша и сообщение о невозможности обновления. Пустой календарь при наличии записей в кэше показывать не допускается. При превышении лимита запросов клиент должен замедлиться. Эти правила согласованы с документацией поставщика данных [7].

## 2.2 Информационная модель и модуль прогноза

Информационная модель приложения намеренно узкая. Хранить нужно не «всё о футболе», а тот минимум, без которого нельзя ни показать календарь, ни посчитать прогноз, ни объяснить цифру.

Единица учёта – матч: идентификаторы и названия двух команд, код соревнования, дата и время в UTC, статус, тур, счёт завершённого матча. Вторая единица – строка турнирной таблицы: место, число игр, мячи, очки. Третья – снимок признаков на конкретный матч: форма, два рейтинга Эло, средние голы, сводка очных встреч, места в таблице, сколько сыгранных матчей лиги лежит в кэше на дату расчёта. Четвёртая – результат расчёта: три вероятности 1 / X / 2 и предварительный счёт (два целых, вероятность клетки, два ожидаемых гола).

Данные с сети не идут в интерфейс напрямую. Они оседают в локальном кэше SQLite. Для ещё не сыгранных матчей снимок считается свежим шесть часов, для завершённых и для таблицы – сутки. Это не промышленная СУБД и не «база предприятия»: это кэш, чтобы не превысить лимит бесплатного тарифа (десять запросов в минуту) и чтобы прогноз на одном и том же срезе фактов воспроизводился [7], [15]. Схема основных таблиц кэша показана на рисунке (рисунок: таблицы кэша SQLite) и подробно описана в приложении Б.

История, из которой считаются Эло и средние голы, обрезается строго: только матчи той же лиги со статусом «завершён» и с датой раньше прогнозируемой встречи. Матч не имеет права видеть свой будущий счёт.

### Поля, которые считаются фактом

Для оперативного контура из документации football-data.org v4 в доменную модель матча переносятся: идентификатор, дата UTC, статус, тур, идентификаторы и имена хозяев и гостей, голы полного времени, признак победителя [7]. Для таблицы – место, число игр, победы, ничьи, поражения, мячи, очки. Ожидаемые голы, травмы и иные поля, которых нет в используемом тарифе, в фактах не появляются.

### Как из фактов получается 1 / X / 2

Пусть на срез уже посчитаны рейтинги хозяев и гостей и четыре средних по пяти матчам. Если сыгранных матчей лиги меньше четырёх, модуль возвращает только тройку Эло по формулам (2)–(5) главы 1.

Иначе атака и оборона нормируются к уровню лиги 1,35 (ниже 0,4 не опускаются), разница Эло переводится в небольшой множитель, ожидаемые голы ограничиваются отрезком от 0,25 до 4 по формулам (6)–(9). Далее строится сетка (10) и выполняется смесь (11).

Разберём тот же учебный пример, что в главе 1, уже как спецификацию модуля. Исходные оценки:

$$
R_{\mathrm{дом}} = 1600,\quad R_{\mathrm{гост}} = 1580,
$$

$$
G^{\mathrm{заб}}_{\mathrm{дом}} = 2{,}0,\quad G^{\mathrm{пр}}_{\mathrm{дом}} = 0{,}8,
\quad
G^{\mathrm{заб}}_{\mathrm{гост}} = 2{,}2,\quad G^{\mathrm{пр}}_{\mathrm{гост}} = 1{,}0,
$$

число завершённых матчей лиги в кэше равно 20. Тогда

$$
a_{\mathrm{дом}} = 2{,}0 / 1{,}35 \approx 1{,}4815,\quad
d_{\mathrm{дом}} = 0{,}8 / 1{,}35 \approx 0{,}5926,
$$

$$
a_{\mathrm{гост}} = 2{,}2 / 1{,}35 \approx 1{,}6296,\quad
d_{\mathrm{гост}} = 1{,}0 / 1{,}35 \approx 0{,}7407,
$$

$$
\delta = (1600 + 80 - 1580) / 1000 = 0{,}10.
$$

Интенсивности для ветки исхода:

$$
\lambda_{\mathrm{дом}} = 1{,}35 \cdot 1{,}4815 \cdot 0{,}7407 \cdot 1{,}10 \approx 1{,}63,
$$

$$
\lambda_{\mathrm{гост}} = 1{,}35 \cdot 1{,}6296 \cdot 0{,}5926 \cdot 0{,}90 \approx 1{,}17.
$$

Отдельно модуль считает тройку Эло и тройку Пуассона, затем смешивает с весами 0,65 и 0,35 и нормирует. На эталонной реализации получены доли $0{,}4817$, $0{,}2442$ и $0{,}2741$ для 1, X и 2 соответственно. Именно эти три числа видит пользователь как ответ на вопрос о предпочтительном исходе.

### Как из тех же голов получается предварительный счёт

Для счёта рейтинг Эло сознательно выключается. Ожидаемые голы берутся как среднее атаки одной стороны и обороны другой:

$$
\lambda_{\mathrm{дом}} = \frac{G^{\mathrm{заб}}_{\mathrm{дом}} + G^{\mathrm{пр}}_{\mathrm{гост}}}{2},
\qquad
\lambda_{\mathrm{гост}} = \frac{G^{\mathrm{заб}}_{\mathrm{гост}} + G^{\mathrm{пр}}_{\mathrm{дом}}}{2}.
\tag{12}
$$

В примере $\lambda_{\mathrm{дом}} = \lambda_{\mathrm{гост}} = 1{,}50$. На сетке 0…8 выбирается клетка максимальной вероятности. В данном случае это 1:1 с вероятностью около 0,112. Соседние клетки 1:2 и 2:1 имеют меньшие доли. Этот путь не заменяет тройку 1 / X / 2 и не использует округление «вверх хозяевам, вниз гостям».

Вероятность клетки после нормировки хвоста можно записать как

$$
P^{*}(i, j) = \frac{P(X=i, Y=j)}{\sum_{u=0}^{8}\sum_{v=0}^{8} P(X=u, Y=v)},
\tag{13}
$$

а предварительный счёт – как пару $(i^{*}, j^{*})$, максимизирующую $P^{*}(i, j)$ с правилом разрыва связей по близости к $(\lambda_{\mathrm{дом}}, \lambda_{\mathrm{гост}})$.

### Инварианты модуля

Модуль обещает:

– на фиксированном срезе фактов результат тот же;
– три вероятности исхода суммируются в единицу;
– предварительный счёт не зависит от Эло и не совпадает с наивным округлением;
– языковая модель не подменяет расчёт.

Модуль не обещает:

– угаданный точный счёт;
– прибыль;
– учёт травм;
– оперативный счёт в ходе матча без задержки источника.

На бесплатном тарифе протокол и календарь могут приходить с опозданием. Это ограничение источника следует указать в требованиях и в руководстве пользователя [7].

### Роль CSV и обучающих сценариев

Файлы football-data.co.uk с колонками даты, команд, голов и исхода FTR служат длинной историей для ретроспективы и скриптов обучения [8]. Они не подменяют REST-ответ в момент клика по карточке. Такое разделение удерживает информационную модель оперативного контура узкой и проверяемой.

### Детализация кэша как информационной структуры

Локальный файл кэша содержит таблицы меток времени, соревнований, матчей, строк турнирной таблицы, заявок и составов. TTL шесть часов для ещё не сыгранных матчей и сутки для завершённых отражает компромисс между актуальностью и лимитом запросов: истечение TTL даёт право снова сходить в сеть, а пока запись свежа, повторный расчёт обязан давать те же числа. Индекс по коду соревнования и дате ускоряет выборку истории; при порче файла его удаляют и наполняют заново из API.

### Расширенный разбор смеси и согласование с формулой (1)

При рейтингах 1600 и 1580 тройка Эло составляет примерно 0,4850; 0,2423; 0,2727, тройка Пуассона при $\lambda_{\mathrm{дом}} \approx 1{,}63$ и $\lambda_{\mathrm{гост}} \approx 1{,}17$ – примерно 0,4799; 0,2453; 0,2748, смесь – 0,4817; 0,2442; 0,2741. Близость троек в этом примере не универсальна: смесь – компромисс первой версии, а не оптимальные веса на всех лигах. Порог «меньше четырёх сыгранных матчей – только Эло» защищает от сетки на почти пустой истории.

Величины $K_1$ и $K_2$ из наивной схемы и интенсивности (12) совпадают по способу усреднения. Различие начинается после дроби: наивная схема округляет, модуль показывает моду сетки и её вероятность (для $\lambda = 1{,}50$ мода 1:1 около 0,112).

## 2.3 Пользовательский интерфейс

Интерфейс спроектирован как набор экранов одного настольного окна: лиги, календарь дня, карточка прогноза и настройки. Переходы показаны на схеме навигации (рисунок: переходы экранов). Подписи к снимкам экранов согласованы с комплектом рисунков.

При запуске программное обеспечение показывает заставку до окончания начальной загрузки. При отсутствии ключа football-data.org открывается экран настроек, разделы лиг, календаря и прогноза закрыты (требование ФТ-11). Ключи хранятся в локальном файле параметров и в журнал не записываются.

Экран лиг. Отображается перечень соревнований бесплатного тарифа: код, название, страна или регион, признак любимой лиги. Поиск и фильтры сужают перечень. Выбор соревнования задаёт контекст календаря.

Экран календаря. Отображаются матчи выбранной даты по всем доступным соревнованиям либо по выбранной лиге: время, хозяева, гости, статус, итоговый счёт завершённого матча. Допускаются переход на соседний день, группировка по лигам и по командам, поиск команды. Выбор строки открывает карточку прогноза. В широком окне календарь и прогноз размещаются рядом.

Экран прогноза матча. Порядок чтения:

– указание: прогноз статистический, это не совет ставить деньги;
– названия команд, дата и, для завершённого матча, итоговый счёт;
– полоса вероятностей 1 / X / 2;
– предварительный счёт: клетка, вероятность клетки и ожидаемые голы по средним за пять матчей, без рейтинга Эло;
– поясняющие блоки: форма, рейтинг Эло, очные встречи, места в таблице;
– таблица рынков, согласованная с исходом 1 / X / 2;
– при наличии источника – отдельный блок новостей и отдельный блок травм и составов;
– текстовое пояснение после чисел.

Сначала программное обеспечение показывает распределение исхода, затем наиболее вероятную клетку счёта с её вероятностью, затем контекст, затем текст. Текст до чисел показывать не допускается.

При числе завершённых матчей лиги в кэше меньше четырёх карточка показывает только рейтинг Эло и не подменяет малую выборку сеткой Пуассона. Если кэш пуст и сеть недоступна, программное обеспечение должно показать сообщение о невозможности обновления.

Тексты интерфейса – на русском языке. Контраст текста на карточках проверяется на соответствие WCAG AA. Критичная доля сопровождается числом, а не только цветом столбца.

Сценарий первого запуска:

1. Запуск собранного приложения (`.exe` или `.app`).
2. Ввод ключа football-data.org на экране настроек, если ключ ещё не задан.
3. Выбор соревнования в списке лиг либо выбор даты в календаре.
4. Открытие матча и чтение полосы 1 / X / 2, предварительного счёта и таблицы рынков.
5. При наличии текстового пояснения – сверка текста с уже показанными числами.

Сценарий не включает приём ставок.

### Производительность, константы и краевые случаи

Объём кэша одной лиги на горизонте сезона измеряется сотнями матчей; для такого объёма SQLite с индексом по соревнованию и дате достаточен [15]. Узким местом остаётся сеть и лимит 10 запросов в минуту, а не арифметика Пуассона на сетке 0…8. Послойная схема упрощает тесты: модели проверяются на синтетических признаках, клиент API – на локальных образцах, без обращения к живому API.

В первой версии зафиксированы константы, которые нельзя молча менять в тексте и в коде порознь: стартовый рейтинг 1500, K-фактор 20, домашнее преимущество Эло 80 пунктов, коридор ничьей в ветке Эло от 0,18 до 0,32, среднее лиги 1,35, пол относительной атаки и обороны 0,4, клип интенсивностей от 0,25 до 4, потолок сетки 8, веса Пуассона 0,65 и Эло 0,35, порог «только Эло» при числе завершённых матчей меньше 4, окно средних голов 5 матчей, TTL кэша 6 ч и 24 ч.

Если команда впервые появляется в кэше, её рейтинг равен 1500. Если сыгранных матчей меньше пяти, среднее считается по имеющемуся числу игр. Пустая таблица отображается тире, а не нулевыми местами. Пустые гербы не блокируют расчёт. Доменные сущности описывают матч, признаки и вероятности; представление не вызывает Эло напрямую.
