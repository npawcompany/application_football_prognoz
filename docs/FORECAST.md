# Расчёт прогноза: факты, оценки, вывод

Этот документ описывает **то, что уже делает код** на рабочей ветке, а не желаемую модель «на будущее». Источник истины:

- сбор фактов — `src/football_prognoz/services/features.py`
- Elo — `src/football_prognoz/models/elo.py`
- вероятности 1X2 — `src/football_prognoz/models/predictor.py`
- карточка матча — `src/football_prognoz/services/matches.py` → `ui/views/match_detail.py`
- текст «почему так» — `src/football_prognoz/ai/explainer.py`

Прогноз **не является** советом ставить деньги. Числа — статистическая оценка, не гарантия счёта.

---

## 1. Три слоя, которые нельзя путать

| Слой | Где в коде | Пример | Это истина? |
| --- | --- | --- | --- |
| **Факт** | протокол API / CSV, кэш SQLite | «Арсенал — City, 26.09.2026, статус SCHEDULED»; «в прошлый тур хозяева выиграли 2:1» | Да, если поле есть у football-data.org v4 |
| **Оценка** | `FeatureService`, `build_elo` | Elo 1610; средние голы за 5 матчей 1.80 | Нет. Пересчитается после нового тура |
| **Вывод** | `Predictor.predict` → `Probabilities` | P(1)=0.41, P(X)=0.27, P(2)=0.32 | Нет. Это прогноз. Сумма всегда 1 |

Правило продукта:

> Языковая модель не считает, кто победит. Она только пересказывает JSON фактов и уже посчитанные вероятности. Если поля нет в football-data.org v4 — его нет: ни xG, ни травм, ни состава.

Наивная схема «5 матчей + округление вверх/вниз» в движок экрана «Прогноз» **не входит**. Она разобрана отдельно как базовая линия для ВКР: [HEURISTIC_FIVE_MATCH.md](HEURISTIC_FIVE_MATCH.md).

## 2. На что опираемся

Опора живого контура — не коэффициент букмекера и не ChatGPT.

1. **Календарь и протоколы** football-data.org REST v4 (12 бесплатных лиг). Поля матча, которые маппим: `id`, `utcDate`, `status`, `matchday`, команды, `score.fullTime`, `score.winner`. Таблица: место, игры, мячи, очки. Полный список — [DATA_SOURCES.md](DATA_SOURCES.md).
2. **История только до матча.** `FeatureService.build` берёт завершённые матчи той же лиги с `utc_date < match.utc_date`. Подглядывания в будущий счёт нет.
3. **Две согласованные модели 1X2**, которые смешиваются:
   - рейтинг **Elo** по всем завершённым матчам в кэше лиги;
   - **независимый Пуассон** по средним голам за последние 5 игр, сдвинутый Elo.
4. Если в кэше меньше **4** сыгранных матчей лиги — Пуассон не запускается, остаётся только Elo. Малая выборка не маскируется сеткой голов.

CSV football-data.co.uk (`FTHG`, `FTAG`, `FTR`) — длинная история для обучения и ретроспективы (`scripts/train.py`), не источник цифры на экране в момент клика «Прогноз».

## 3. Что берём в факты

Факт — то, что пришло из API/CSV и лежит в SQLite. Ниже закрытый список для одного прогноза.

### 3.1. Каркас матча

- идентификаторы и имена хозяев / гостей;
- код соревнования (`PL`, `PD`, `SA`, …);
- дата UTC, тур, статус (`SCHEDULED` / `TIMED` / `FINISHED` / …);
- гербы, если CDN отдал файл.

Это ещё не сила команды. Без этих полей матч нельзя ни показать, ни посчитать.

### 3.2. Состоявшиеся счета истории

Для каждого завершённого матча лиги до даты прогноза:

- голы хозяев и гостей (`score.fullTime`);
- кто выиграл (`HOME_TEAM` / `AWAY_TEAM` / `DRAW`), либо вывод из счёта.

Счёт 2:1 — факт. «Заслуживали 2:1» — не факт: xG в free v4 нет, и explainer явно не имеет права его выдумывать.

### 3.3. Таблица

Место хозяев и гостей в текущей таблице лиги — факт протокола. В формулу λ оно **не входит**: это контекст для экрана и для LLM.

### 3.4. Что сознательно не факт в этой версии

В JSON explainer и в `Predictor` нет и не должно появиться «из воздуха»:

- травмы, состав, удаления, погода;
- xG, удары в створ, владение;
- live-счёт на бесплатном тарифе (он с задержкой, продукт не сканер);
- коэффициенты букмекера как «наш» прогноз.

H2H и строка формы `WWDLW` — факты-агрегаты из тех же счетов. Они показываются человеку. В λ они не подставляются напрямую.

## 4. Что модель оценивает из фактов

Оценки собирает `FeatureService` (`form_n = 5`).

| Оценка | Как считается | Кто её ест |
| --- | --- | --- |
| `home_elo` / `away_elo` | Все завершённые матчи лиги по времени, старт 1500, K = 20, дом +80 к ожиданию | `Predictor` и UI |
| `home_recent_goals_for/against` и то же у гостей | Среднее забитых / пропущенных в последних 5 матчах команды (дом и выезд вместе) | только `Predictor` |
| `sample_matches` | Число завершённых матчей лиги в кэше до даты | порог «Elo-only», UI |
| `home_form` / `away_form` | Строка W/D/L по тем же 5 матчам | UI + explainer, **не** формула λ |
| `h2h_summary` | До 5 очных в кэше, счётчик побед/ничьих | UI + explainer, **не** формула λ |
| `home_position` / `away_position` | Строка таблицы | UI + explainer, **не** формула λ |

Важная честность: на экране «фактами» выглядят форма, таблица и H2H. Движок 1X2 опирается на **Elo и средние голы**. Форма и место в таблице — пояснение человеку, не второй классификатор.

### 4.1. Как считается Elo

Идём по сыгранным матчам лиги в порядке `utc_date`.

Ожидание победы хозяев:

\[
E_{\text{home}} = \frac{1}{1 + 10^{(R_{\text{away}} - (R_{\text{home}} + 80)) / 400}}
\]

Факт результата: победа = 1, ничья = 0.5, поражение = 0. Обновление:

\[
R \leftarrow R + 20 \cdot (\text{факт} - \text{ожидание})
\]

Если команды ещё не было в кэше — 1500.

Из двух рейтинга в 1X2 (`elo_1x2`):

- доля «не ничья» делится по тому же \(E_{\text{home}}\);
- вероятность ничьей: \(0.27 - 0.06 \tanh(|\Delta|/200)\), зажата в \([0.18, 0.32]\). Ничья не выпадает из модели: при равных силах она около 27%, при разгроме падает, но не ниже 18%.

## 5. Как выводится результат одного матча

Цепочка в коде одна: `MatchService.forecast` → фичи → `Predictor.predict` → explainer → UI.

### Шаг A. Срез кэша

История лиги до `match.utc_date`, только `FINISHED` / `AWARDED`. Если матчей \(< 4\) — сразу Elo 1X2, Пуассон не считается.

### Шаг B. Ожидаемые голы λ (если выборка достаточна)

Константа лиги в коде сейчас **не оценивается**, а задана:

`LEAGUE_AVG_GOALS = 1.35` (примерно 2.7 гола на матч).

Сила атаки и обороны — отношение недавних голов к этой константе, пол не ниже 0.4:

```text
home_att = max(0.4, home_recent_goals_for    / 1.35)
home_def = max(0.4, home_recent_goals_against / 1.35)
away_att = max(0.4, away_recent_goals_for    / 1.35)
away_def = max(0.4, away_recent_goals_against / 1.35)
```

Сдвиг Elo (дом уже внутри: +80):

```text
elo_diff = (home_elo + 80 - away_elo) / 1000
```

Интенсивности, затем клип в \([0.25, 4.0]\):

```text
λ_home = clip(1.35 × home_att × away_def × (1 + elo_diff))
λ_away = clip(1.35 × away_att × home_def × (1 − elo_diff))
```

Это не Dixon–Coles: нет ρ на низкие счета, нет отдельного множителя γ как у Махера. Домашний фактор сидит в Elo (+80) и в `elo_diff`. Независимый Пуассон — сознательное упрощение v1.

### Шаг C. Сетка счетов 0…8

Для каждой клетки \((i, j)\):

\[
P(i,j) = \mathrm{Poisson}(i;\lambda_{\text{home}}) \cdot \mathrm{Poisson}(j;\lambda_{\text{away}})
\]

Сумма клеток \(i>j\) / \(i=j\) / \(i<j\) даёт Пуассон-1X2. Потолок 8 голов; хвост отбрасывается, затем `Probabilities.normalized()` возвращает сумму ровно 1.

Точный счёт на экран **не выводится**. Сетка нужна только как способ получить 1 / X / 2. Округлять λ до «2:1» продукт запрещает: это как раз наивная эвристика.

### Шаг D. Смесь 65 / 35

```text
итог = 0.65 × Пуассон-1X2  +  0.35 × Elo-1X2
```

Потом снова нормализация. Детерминизм: на тех же фичах `Predictor` всегда даёт те же три числа (это проверяет тест).

### Шаг E. Что видит человек

1. Три вероятности 1 / X / 2 и полоска (сумма 1).
2. Блок «фактов»: форма, Elo, H2H, место в таблице, число матчей в кэше.
3. Ярлык фаворита — `Probabilities.favorite_label`: наибольшая из трёх долей (`1`, `X` или `2`). Без самой вероятности это не расчёт.
4. AI-текст **только если** настроен OpenAI/Ollama. Иначе числа всё равно на месте, баннер «AI не настроен».

JSON, который разрешено отдать LLM: имена команд, лига, дата, три вероятности, форма, Elo, H2H, места, `sample_matches`. Средние голы в этот JSON сейчас **не попадают** — explainer не видит λ, только итог 1X2 и контекст. Выдумывать травмы и xG промпт запрещает.

## 6. Числовой пример по тем же формулам

Возьмём фикстуру из `tests/test_predictor.py`: хозяева Elo 1600, гости 1580; средние голы 2.0 / 0.8 у хозяев и 2.2 / 1.0 у гостей; в кэше 20 матчей.

```text
home_att = 2.0 / 1.35 ≈ 1.48
home_def = 0.8 / 1.35 ≈ 0.59
away_att = 2.2 / 1.35 ≈ 1.63
away_def = 1.0 / 1.35 ≈ 0.74
elo_diff = (1600 + 80 − 1580) / 1000 = 0.10

λ_home ≈ 1.35 × 1.48 × 0.74 × 1.10 ≈ 1.63
λ_away ≈ 1.35 × 1.63 × 0.59 × 0.90 ≈ 1.17
```

Дальше сетка 0…8 и смесь с Elo. Итог на экране — три доли, не «будет 2:1». Даже если λ близки к 1.63 : 1.17, наиболее вероятная клетка сетки и математическое ожидание — разные вещи; продукт клетку не показывает именно поэтому.

Что здесь факт? Только прошлые счета и расписание. λ, Elo и 41/27/32 — вывод.

## 7. Правила честности, которые уже зашиты в тесты

- Сумма `p_home + p_draw + p_away` равна 1 (`test_probabilities_sum_to_one`, `normalized()`).
- На фиксированных фичах прогноз детерминирован.
- Сильнее атака / выше Elo хозяев → `p_home` растёт.
- Explainer без LLM возвращает `None`; в промпте нет команды «угадай счёт».
- Клиент API в тестах ходит только в `data/samples/`, не в живой REST.

Калибровка на длинной выборке (Brier, log-loss, сравнение с эвристикой 5 матчей) — задача п. 3.3 ВКР и `scripts/train.py`, не то, что рисует UI сегодня.

## 8. Карта «кто на что влияет»

```text
football-data.org / CSV
        │  факты: дата, статус, счёт, таблица
        ▼
   SQLite-кэш (TTL 6 ч расписание / 24 ч результаты)
        │
        ▼
 FeatureService ──► форма, H2H, таблица ──────────────► UI + LLM
        │
        ├── Elo (вся история лиги)
        └── средние голы за 5 матчей
                │
                ▼
         Predictor
           sample < 4  → только Elo 1X2
           иначе       → λ → Пуассон 0…8 → смесь 65/35
                │
                ▼
         Probabilities (1 / X / 2)
                │
                ├── UI: полоска вероятностей
                └── Explainer: текст 2–4 предложения, без новых фактов
```

## 9. Короткий устав

1. Факт — поле протокола и кэша. Нет поля в v4 — нет факта.
2. Опора расчёта — Elo по истории лиги и средние голы за 5 матчей; не округление «точного счёта» и не LLM.
3. Сначала λ и сетка, потом только 1X2. Точный счёт пользователю не выдаём как «будет».
4. Форма, H2H и таблица объясняют карточку; в смесь 65/35 они не входят.
5. Ярлык «1» — наибольшая доля, рядом обязаны стоять три процента.
6. Рынок и xG в v1 не подменяют локальную модель.

Если формула на экране расходится с этим файлом — ошибка в коде или в документе. Править нужно так, чтобы они снова совпали.
